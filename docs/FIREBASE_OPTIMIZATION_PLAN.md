# Firebase and UI optimization plan

Reviewed 14 October 2026. Preferences: lowest Firebase usage; incremental changes to the existing Firebase, FastAPI, Pub/Sub, Next.js, React Query, and Zustand stack.

## Findings and baseline

This review used source inspection, an in-process synthetic repository trace, and existing tests. Production traffic, billing, and browser frame timings were not measured. Prioritization is based on demonstrated amplification in the code, rather than a claimed production cost estimate.

- **Duplicate browser refresh mechanisms.** `frontend/lib/workspace.tsx` polls Studio every 15 seconds during work and subscribes to every project run summary. Every snapshot, including the initial snapshot, invalidates both Studio and conversation queries. Chat separately polls every 2.5–5 seconds in `frontend/components/chat-workspace.tsx`; saves poll the job endpoint every second. Mutations also combine broad invalidation and explicit refetch. Active chat and Studio alone can issue approximately 28 requests/minute before snapshot-triggered and mutation-triggered requests.
- **Scoped Studio queries discard project-wide reads.** `backend/tools/studio_commands.py` first loads 60 project jobs, 20 runs, and 20 approvals, then overwrites those results when a conversation is selected. The replacement queries retrieve all matching documents before slicing in Python. The endpoint also reloads up to 100 assets, their lifecycle documents, brand, budget, and 60 events.
- **Repeated document and identity reads.** Read handlers repeatedly call authorization through nested helpers. Provisioning starts a transaction on each authenticated API request, and some commands provision again. `_artifact()` fetches lifecycle metadata that `asset_content()` fetches again. `conversation_state()` loads run jobs, then production dependencies, then conversation jobs again. The preview endpoint reads and unpacks the composition twice. `UnitOfWork.get()` caches pending writes but does not memoize repeated underlying reads.
- **Unbounded history scans.** Project discovery reads every project and filters membership in Python. Conversation lists read and sort the entire collection. Conversation schedulers repeatedly read all messages, even though director context needs only the latest 12. ADK session queries fetch all sessions/events before applying filters or recent-event limits. `infrastructure/firestore.indexes.json` currently defines no composite indexes.
- **Worker polling amplifies writes.** Each unfinished provider poll moves the job through `claimed` and `waiting_for_provider`. Each transition writes a job, run, run summary, step, and event. Including outbox scheduling and dispatch acknowledgement, one unchanged provider poll can write approximately 12 documents. Provider polling is fixed at 10 seconds.
- **Sweeps repeatedly inspect idle state.** Dispatcher, reconciler, workflow, and conversation schedulers enumerate projects. Conversation sweeps inspect each conversation's messages and active run. Workflow advancement writes claim/release leases even when dependency state has not changed. Reconciliation can reset a provider's scheduled poll time to now without first respecting a future `next_poll_at`.
- **Playback causes broad rendering.** Workspace, chat, timeline, tools, and previews subscribe to the entire Zustand store. Player time updates therefore propagate through large component trees and the workspace context. Media thumbnails, waveforms, audio previews, and private media independently download and decode the same assets. Transient Studio query errors currently reset the editor and head, which can discard unsaved work.

Verified baseline:

- 30 tests passed across `test_firestore_reads.py`, `test_worker_polling.py`, and `test_conversations.py`; one existing Starlette deprecation warning.
- `npm run check:web` passed.
- Synthetic API trace: with 65 unrelated image jobs and one empty conversation, unscoped Studio performed 87 document returns/point reads; scoped Studio performed 90, including 80 discarded job/run documents. No assets were seeded. This trace excludes empty-query minimum charges, index-entry reads, transaction retries, Firebase Auth calls, and listener/rules reads.

## Phase 1 — Bound reads and establish useful measurements

Deliver this phase before changing refresh behavior, so existing clients immediately become cheaper.

- Add repository query operations that apply filters, ordering, limits, and value cursors in Firestore. Implement equivalent semantics in the memory repository. Batch document retrieval reduces round trips; it does not reduce the number of billed documents.
- Branch on conversation scope before issuing Studio history queries. Query jobs/runs/approvals by `conversation_id` and descending creation time with server-side limits of 60/20/20. Explicitly fetch the active run and its required dependencies when they fall outside history windows; history limits must not hide active work or reused jobs.
- Query conversation lists by descending `updated_at` with a document-ID tie-breaker and `limit + 1`. Use an opaque value cursor, while accepting the old ID-only cursor during migration. Filter project discovery by membership using an indexed `member_uids` array maintained with the existing authoritative `members` map. The backend continues to enforce roles and OAuth project scope.
- Build one request-scoped read context for read handlers: memoize user, project, conversation, artifact/lifecycle, run, and job reads. Reuse the same dependency map for run results and production summaries. Keep transaction authorization fresh; never carry a read-handler cache into a mutation or worker transaction. Memoize `UnitOfWork` reads within each transaction attempt, returning defensive copies and honoring pending writes/deletes.
- Verify Firebase identity once per API request, preserving revocation/disabled checks. Reuse that verified identity in nested read helpers; native/MCP commands and workers retain their own invocation checks. Provision missing users transactionally after a cheap existence read, rather than opening duplicate provisioning transactions for existing users.
- Load and unpack composition packages once per preview request. Cache immutable storyboard/package bytes by content hash in a bounded process-local LRU; recheck caller access and lifecycle availability before reuse. Do not cache authorization decisions across requests.
- Filter ADK sessions and recent events in Firestore when the caller supplies filters/limits; preserve full-history retrieval for resume/export paths that require it. Replace scheduler full-message scans with bounded pending-message queries and a 12-message tail for director context.
- Instrument repository operations with caller/endpoint or worker-stage labels, returned document counts, transaction attempts, committed writes, and latency. Measure identity calls separately. Never log tokens, prompts, or media bytes. Counters are application-level evidence, not exact billing; compare deployed Firestore usage and Query Explain results separately.

Public changes: additive repository query interfaces; project `member_uids`; versioned conversation cursors. Existing endpoint shapes and command/idempotency contracts stay compatible.

## Phase 2 — One refresh owner and separate resource lifetimes

- Move active conversation polling into the workspace data layer. Remove the browser's project-wide run-summary listener and independent chat/Studio timers for the cost-first default. Existing run summaries remain available for compatibility until their other consumers are audited.
- Poll the bounded conversation endpoint every 30 seconds while work is queued/running; increase to 60 seconds after two unchanged responses and return to 30 seconds after visible progress. Stop recurring polling for completed, approval-waiting, and reconciliation-waiting states. A queued user request or another active operation overrides a paused run and keeps polling alive.
- Fetch once on opening a conversation, after a successful mutation, on manual refresh, and when a stale visible tab reconnects/refocuses. Suspend recurring polling in hidden/offline tabs. Active generation may therefore take up to 60 seconds to appear, excluding worker scheduling and network latency; this is the chosen cost tradeoff. Remote changes to an idle view appear on refocus/manual refresh.
- Split Studio's resource lifetimes with additive endpoints: project metadata/brand/budget, paginated run/approval history, and paginated events. Keep `/studio` as a compatible bootstrap/legacy endpoint. The active conversation response owns messages, operations, current run, and production progress; obtain a current standalone preview approval there too. Query assets through the existing paginated asset endpoint only when needed, starting with 20 items.
- Update current composition heads from conversation responses; invalidate budget/assets/history only when an operation changes those resources. Do not reload all resources on every job transition. Use distinct query-key families for conversation list, conversation state, assets, metadata, and immutable composition/storyboard revisions.
- Use React Query freshness explicitly: mutable metadata/history/assets 60 seconds; immutable revision content `staleTime: Infinity` with authorization failures clearing private data. Apply cancellation signals to all query requests and abort old-scope work on navigation/sign-out.
- Replace generic `action()` refresh-all behavior with mutation-specific cache updates/invalidation. Insert a pending local message immediately, reconcile it using the existing idempotency key/server ID, and keep it visible with retry controls on failure. Optimism never approves a revision or declares an export successful.
- Replace the save loop with a persistent pending-save operation observed by the same refresh owner. Check a newly submitted save after 2 seconds, then use 5/10/20/30-second backoff while pending. During a save, that timer replaces the normal timer and requests only the exact save job; reload conversation state once the job completes. Preserve edits made while saving; after completion advance `expected_head` without overwriting newer local edits. After the existing one-minute wait, show a recoverable pending state instead of treating the save as failed; stopping observation on unmount does not cancel durable work.
- Preserve the timeline on transient network/429/5xx failures and display stale/reconnecting status. Clear private state on sign-out, identity change, or definitive access denial. Parse `Retry-After`, expose it through CORS, and retry no sooner than that delay with jitter; stop automatic retries for 401/403 and preserve idempotency keys across ambiguous mutation outcomes.

Public changes: additive lightweight project/history/event endpoints, approval data in conversation state, optional mutation response fields for cache reconciliation, and `ApiError.retryAfterMs`. No new streaming service or browser Firestore write permission is required.

## Phase 3 — Reduce worker reads and unchanged-status writes

- Keep provider-poll lease acquisition and generation fencing on the job document without changing its user-visible status. If the provider is still pending, update only the job's operation/scheduling/lease fields and its outbox record. Do not increment run versions or write steps/events/summaries for an unchanged provider result. Retain normal transitions for initial submission, actual status changes, errors, cancellation, materialization, and completion.
- Back off pending provider polls from 15 to 30 to 60 seconds, with persisted attempt count and deterministic bounded jitter; reset on meaningful provider progress. Honor provider retry guidance when available. Preserve known operation handles and never resubmit a known operation merely because polling failed.
- Add indexed collection-group queries for pending outbox records with `next_attempt_at <= now`, ordered by due time and limited to 100 per batch. Reconciliation scans only due/expired nonterminal jobs, using a persisted `reconcile_after` scheduling field. Respect future polls and live leases; operator-driven uncertainty resolution remains explicit.
- Discover pending conversation messages and changed runs using indexed work/status queries, rather than enumerating every project/conversation. Advance only the owning conversation/run. Use existing Pub/Sub delivery paths to trigger advancement after job execution and API message/approval changes, with durable wake markers in existing outbox documents and version fencing so crashes cannot lose advancement. Store processed wake/dependency versions in existing run/conversation records; unchanged sweeps skip lease transactions.
- Keep the one-minute scheduled reconciliation as a bounded recovery mechanism during rollout. Avoid rapid duplicate sweeps in the emulator/local pump. A due provider poll, lease recovery, and workflow advancement must remain distinct operations.
- Keep durable budget settlement, command idempotency, candidate recovery, cancellation fencing, and ADK event persistence. Do not batch away durability boundaries or drop required conversation events to save writes.

Public changes: internal queue message kind for workflow wake-ups; optional scheduling/version fields on jobs, runs, conversations, and outbox records; collection-group indexes. Use read defaults for legacy records until backfill completes.

## Phase 4 — Isolate rendering and reuse private media

- Replace full-store subscriptions with narrow Zustand selectors. Split workspace data/actions from playback state. Memoize message/scene/clip components so playhead updates affect only the transport and playhead, not chat, media cards, or query owners. Throttle React playback-time publication to at most 10 Hz; the player owns smooth playback, and scrubbing updates immediately.
- Add a shared in-memory media loader keyed by UID, project, artifact, and content hash. Deduplicate simultaneous downloads, thumbnail sampling, and waveform decoding. Reference-count object URLs; use a 64 MiB/20-entry LRU budget with five-minute expiry for unused entries, and promptly evict unused originals after generating small derivatives. Abort an underlying request only when no consumers remain.
- Lazy-load historical/offscreen media with IntersectionObserver and paginate older messages. Reuse sampled thumbnails by artifact/source timestamp and decoded waveform peaks by artifact hash. Avoid downloading every video simply to display an offscreen card. Keep the existing private-content endpoint, hash verification, opaque preview sandbox, and shared playback ownership.
- Clear the media cache on identity change or definitive access denial. The cache is tab-local; persistent offline media and signed public download URLs are outside this change.

## Acceptance, rollout, and defaults

Implement as four reviewable changes in phase order. Deploy indexes first, then backward-compatible server changes, then the client, then worker scheduling changes. Make backfills resumable/dry-runnable and gate new query paths until complete; do not leave full-scan fallbacks enabled after migration.

- Expand read-count tests to count query results and transaction attempts, not only point `get()` calls. Seed 1,000 unrelated jobs/runs, 1,000 conversations, long message history, old active runs, and reused dependencies. Scoped requests must not read unrelated history; page work must scale with page size rather than collection size.
- Prove unchanged provider polls write at most three documents per cycle including dispatch acknowledgement: job, outbox, and outbox acknowledgement. Count necessary long-poll lease heartbeats separately. They must write zero run/summary/step/event documents. Prove unchanged workflow/conversation sweeps commit zero lease writes.
- Use fake-clock browser tests to assert one polling owner, 30/60-second backoff, zero recurring idle/hidden/offline refreshes, targeted mutation refreshes, resumable pending saves, and `Retry-After` handling. Test queued requests behind approvals and reconciliation, remote changes on refocus, and rapid conversation switching.
- Preserve existing authorization, membership removal, OAuth revocation, exact-head approvals, concurrent edits, save-while-editing, cancellation, duplicate Pub/Sub delivery, uncertain submission, budget accounting, and restart-recovery tests. Test both memory and real Firestore emulator query behavior. Add index/deployed Query Explain verification because emulator success does not establish deployed query cost or index readiness.
- Assert simultaneous consumers download/decode each immutable asset once, private caches do not cross users, and URL cleanup respects remaining consumers. Profile a representative timeline during playback: chat/clip cards must not commit renders on each time update; inspect main-thread tasks and interaction latency before/after rather than claiming an unmeasured FPS gain.
- Re-run backend tests, Firestore/Storage rules tests, frontend TypeScript/build, and the existing Playwright workflow suite. Compare requests/minute, returned documents/request, writes/provider cycle, idle worker reads, error rates, and save/generation completion latency after each rollout stage. Keep the previous refresh/scheduling configuration available for rollback; new fields and endpoints are additive.

Assumptions: delayed progress is acceptable in exchange for minimum database use; one-minute recovery scheduling remains initially; approvals, budgets, durable history, and access revocation are correctness constraints. No Redis, database migration, cross-request permission cache, or separate materialized workspace document is introduced. A materialized view would add writes and should only be considered after the bounded-query baseline demonstrates a remaining read bottleneck.

Reference checks:

- [Firestore billing](https://firebase.google.com/docs/firestore/pricing): listener reconnects, security-rule dependencies, index reads, and empty-query minimums can add billed reads; do not treat repository counters as invoices.
- [Firestore queries](https://firebase.google.com/docs/firestore/query-data/queries) and [Query Explain](https://firebase.google.com/docs/firestore/query-explain): apply filters/limits in the database and verify index behavior.
- [React Query defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults): cached queries are stale by default, and intervals are independent of `staleTime`.
- [Firebase session management](https://firebase.google.com/docs/auth/admin/manage-sessions): retain revocation checking while removing redundant checks within one request.
